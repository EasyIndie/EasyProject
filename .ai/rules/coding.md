# 编码规则

> **📜 所有 AI Agent 和开发者必须遵守此编码规则。无一例外。**

---

## 核心原则

| 原则 | 说明 |
|------|------|
| **可读性优先** | 代码是写给人（和 AI）读的，机器执行只是副产品 |
| **单一职责** | 一个函数只做一件事 |
| **命名即文档** | 好的命名不需要注释来解释 |
| **显式优于隐式** | 不要隐藏行为，不要魔法 |
| **简单优于聪明** | 朴素的方案优于炫技的方案 |

---

## 命名规范

### 通用规则

- **有意义的名字**：`userRepository` 而不是 `ur`
- **不使用缩写**：`calculateTotalPrice()` 而不是 `calcTotPrc()`
- **布尔值用 is/has/can 前缀**：`isActive`、`hasPermission`、`canEdit`
- **常量用大写蛇形**：`MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT_MS`

### 语言习惯

不同语言遵循各自的社区惯例：

| 语言 | 变量/函数 | 类/接口 | 常量 | 文件名 |
|------|-----------|---------|------|--------|
| TypeScript | camelCase | PascalCase | UPPER_SNAKE | kebab-case |
| Python | snake_case | PascalCase | UPPER_SNAKE | snake_case |
| Go | camelCase | PascalCase | PascalCase | snake_case |
| Rust | snake_case | PascalCase | UPPER_SNAKE | snake_case |

## 函数设计

```
✅ 好的函数：
  - 短小（通常不超过 30 行）
  - 只做一件事
  - 参数不超过 4 个（超过用对象/结构体）
  - 没有副作用（或副作用明确标注）
  - 返回值类型明确

❌ 坏的函数：
  - 超过 50 行
  - 做多件事（函数名中有 "and" 是坏信号）
  - 参数超过 5 个
  - 修改全局状态
  - 返回多种不相关的类型
```

---

## 错误处理

- **不要吞掉错误**：每个 catch 块必须有显式的处理逻辑
- **尽早失败**：在输入验证阶段就拒绝无效数据
- **错误信息要有用**：包含"什么出错了"和"为什么"
- **不要用异常做流程控制**：异常用于异常情况

---

## 注释

- **注释解释"为什么"，而不是"什么"**：代码已经说了"什么"
- **不要注释掉的代码**：删除它，Git 历史可以找回
- **TODO 必须关联 Issue**：`// TODO(#123): 实现缓存策略`
- **公共 API 必须有文档注释**：每个公开函数/类/接口都要说明用途

---

## 文件组织

- **文件不超过 500 行**：超过则考虑拆分
- **一个文件一个主要概念**：UserService.ts 只包含用户相关的服务逻辑
- **目录内文件数不超过 15 个**：超过则考虑引入子目录

---

## 代码审查检查清单

在提交代码前，自问：

```
□ 这段代码容易理解吗？
□ 命名准确表达了意图吗？
□ 有没有更简单的实现方式？
□ 错误都处理了吗？
□ 有没有遗留的调试代码或注释掉的代码？
□ 有没有硬编码的值应该提取为常量？
□ 依赖方向正确吗（高层不依赖低层细节）？
```

---

## AI Agent 特别提示

- **每次生成代码后**，对照本文件自审
- **不确定命名时**，参考项目中已有的命名模式
- **如果找不到合适的名字**，停下来思考是否抽象错了
- **不要因为"AI 写的"就降低标准**
