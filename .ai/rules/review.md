# 审查规则

> **📜 代码审查标准。每个 PR 都必须经过审查。**

---

## 审查流程

```
开发者提交 PR → AI Agent 自审 → 人工/AI 审查者审查 → 修改 → 批准 → 合并
```

---

## 审查检查清单

### 1. 功能正确性

```
□ 代码实现了 PR 描述中的所有功能？
□ 是否满足 tasks/ 中定义的验收标准？
□ 有没有遗漏的边界条件？
```

### 2. 代码质量

```
□ 命名清晰有意义？
□ 函数/方法长度合理（不超过 50 行）？
□ 有没有重复代码可以提取？
□ 有没有过度设计（为不需要的未来写代码）？
```

### 3. 标准合规

```
□ 是否符合 docs/standards/coding.md？
□ 如果涉及 API，是否符合 docs/standards/api.md？
□ 如果涉及数据库，是否符合 docs/standards/database.md？
```

### 4. 安全性

```
□ 有没有 SQL 注入风险？
□ 有没有 XSS 风险？
□ 敏感信息是否被记录到日志？
□ 权限检查是否到位？
```

### 5. 测试

```
□ 新代码有对应的测试？
□ 现有测试全部通过？
□ 测试覆盖了主要路径和边界条件？
```

### 6. 文档

```
□ 公共 API 有文档注释？
□ README 是否需要更新？
□ 是否需要新的 ADR？
```

---

## 审查反馈原则

| 原则 | 说明 |
|------|------|
| **具体** | 指出具体代码行，不要笼统地说"这里有问题" |
| **可操作** | 告诉对方怎么改，不要只说"不好" |
| **讲道理** | 解释为什么这样更好，不要只说"改成这样" |
| **对事不对人** | 评论代码，不评论人 |
| **区分严重程度** | 用标签标注：🔴 阻塞 / 🟡 建议 / 🟢 锦上添花 |

---

## 审查结果

审查完成后给出明确的结论：

```
✅ Approved  — 可以合并
🟡 Comment  — 有小问题但不阻塞
🔴 Changes  — 必须修改后才能合并
```

---

## AI Agent 特别提示

- **审查时对照 `.ai/rules/` 检查**：编码、Git、文档规则都要查
- **审查报告要具体**：指出哪个文件的哪一行有什么问题
- **同时检查"多了什么"和"少了什么"**：死代码和遗漏的测试
- **不确定时标注为 Comment**：不要因为不确定就阻塞 PR
