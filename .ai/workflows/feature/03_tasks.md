# 步骤 3：任务拆解

> **📌 将设计方案拆解为小而可执行的任务。每个任务应该是半天到一天的工作量。**

---

## 目标

将架构设计方案拆解为一组有序的、可独立完成的任务。每个任务有明确的输入、输出和验收标准。

---

## 操作步骤

### 1. 从设计方案中提取工作项

遍历设计方案中的「涉及文件」和「数据库变更」，识别出独立的工作单元。

### 2. 按依赖排序

```
正确的顺序：
  数据模型 → 业务逻辑 → API 接口 → 前端页面 → 测试

错误的顺序：
  先写 API 接口（没有数据模型？）
  先写测试（不知道接口长什么样？）
```

### 3. 拆解原则

| 原则 | 说明 |
|------|------|
| **小而独立** | 每个任务半天到一天完成 |
| **有产出** | 每个任务有明确的产出物（代码文件、测试、文档） |
| **可验证** | 每个任务完成后有方法验证 |
| **依赖清晰** | 明确哪些任务必须先完成 |

### 4. 生成任务文件

对每个任务：

1. 使用 `.ai/templates/task-template.md` 模板
2. 按 `NNNN-short-name.md` 格式命名（NNNN 4 位数字，从已有最大编号 +1）
3. 填写所有字段：目标、背景、文件、计划、检查清单、验收标准
4. 放入 `tasks/todo/`

---

## 输出

```markdown
# 任务拆解：[功能名称]

## 任务列表

| 序号 | 任务 | 依赖 | 预估 |
|------|------|------|------|
| T001 | 创建 User 数据模型 | - | 0.5d |
| T002 | 实现注册接口 | T001 | 1d |
| T003 | 实现登录接口 | T001 | 1d |
| T004 | 实现 JWT 中间件 | T003 | 0.5d |
| T005 | 编写测试 | T002,T003,T004 | 1d |

## 依赖图

```
T001 ──┬── T002 ──┐
       │           ├── T005
       └── T003 ───┤
                   │
                   T004 ──┘
```

## 关键路径

T001 → T003 → T004 → T005（3 天）

## 注意事项

- T002 和 T003 可以并行开发
- T004 依赖 T003 的接口定义
- T005 是所有开发任务的最后一步

## 下一步

所有任务已创建在 tasks/todo/。开始 04_implementation.md。
```

## 检查清单

```
□ 所有涉及的工作都有对应的任务
□ 任务按正确的依赖顺序排列
□ 每个任务有明确的产出物
□ 任务大小合理（半天到一天）
□ 关键路径已识别
□ 所有任务文件已创建在 tasks/todo/
```
