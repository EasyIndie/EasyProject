# 步骤 4：实现

> **💻 逐个实现任务。这是写代码的阶段。**

---

## 目标

按照任务列表逐个实现功能。遵守编码标准，保持代码质量。

---

## 操作步骤

### 对每个待实现的任务，重复以下流程：

### 1. 认领任务

```bash
# 将任务文件从 todo 移动到 doing
mv tasks/todo/0001-xxx.md tasks/doing/
```

### 2. 准备

- 重新阅读任务文件的「目标」、「背景」、「涉及文件」、「实施计划」
- 阅读需要修改的现有文件，理解它们的结构和约定
- 确保理解任务的验收标准

### 3. 创建分支

```bash
git checkout main
git pull origin main
git checkout -b feature/xxx    # 遵循 .ai/rules/branch.md
```

### 4. 实现

遵循以下规则（每次写代码时都要回顾）：

```
□ 我读了 .ai/rules/coding.md 吗？
□ 我读了 docs/standards/coding.md 吗？
□ 我遵循了项目现有的代码风格吗？
□ 函数够短吗（不超过 30 行）？
□ 命名表达了意图吗？
□ 错误处理完整吗？
□ 有没有重复代码可以提取到 packages/？
```

### 5. 提交

遵循 `.ai/rules/git.md`：

```bash
git add <relevant-files>
git commit -m "feat: <简短描述>"
```

**提交信息要求**：
- 使用约定的 type（feat/fix/refactor 等）
- 简短描述（一行总结做了什么）
- 关联任务编号（Refs T001）

### 6. 自检

```bash
# 运行现有测试
make test

# 如果是新功能，运行你写的测试
# 确保没有 break 任何东西
```

### 7. 完成任务

- 将任务文件从 `doing/` 移动到 `review/`
- 在任务文件中填写「Result」：

```markdown
## 结果

### 实际做了什么
- ...

### 遇到的问题
- ...

### 注意事项
- ...
```

### 8. 重复

继续下一个任务，直到所有任务完成。

---

## 实现中的常见情况

### 发现任务范围太大

如果发现一个任务超过 1 天的工作量：
1. 停止
2. 将任务拆分为 2-3 个小任务
3. 更新 `03_tasks.md`

### 发现设计有问题

如果在实现中发现架构设计不合理：
1. 停止
2. 回到 `02_design.md` 重新评估
3. 更新设计文档和 ADR（如果需要）
4. 更新受影响的任务

### 发现需要新增功能

如果需要做任务列表之外的事：
1. 评估是否属于本功能的范围内
2. 在范围内 → 创建新任务
3. 不在范围内 → 记录下来，作为后续功能
