# 步骤 6：审查

> **🔍 自审 + 提交 PR + 审查。质量把关的最后一步。**

---

## 目标

确保代码质量达到可合并的标准，然后提交 PR 并通过审查。

---

## 操作步骤

### 1. 自审

在创建 PR 前，自己先审查一遍代码。使用 `.ai/rules/coding.md` 中的检查清单：

```
□ 代码容易理解吗？
□ 命名准确吗？
□ 有没有更简单的实现？
□ 错误都处理了吗？
□ 有没有调试代码或注释掉的代码？
□ 硬编码的值应该提取吗？
□ 依赖方向正确吗？
```

### 2. 对照审查规则

使用 `.ai/rules/review.md` 的检查清单：

```
□ 功能正确性：代码实现了所有预期功能？
□ 代码质量：清晰、简洁、无重复？
□ 标准合规：符合编码和项目标准？
□ 安全性：无常见安全漏洞？
□ 测试：测试充分且通过？
□ 文档：已更新相关文档？
```

### 3. 清理工作区

```bash
# 确保所有改动都已提交
git status

# 确保分支是最新的
git fetch origin
git rebase origin/main
```

### 4. 创建 PR

推送分支并创建 Pull Request：

```bash
git push origin feature/xxx
# 然后在 GitHub 上创建 PR
```

PR 标题遵循约定式提交格式（`.ai/rules/git.md`）。

PR 描述使用 `.github/PULL_REQUEST_TEMPLATE/pull_request_template.md` 模板：

```markdown
## 做了什么
（简述变更）

## 关联任务
Closes T001, T002, T003

## 变更类型
- [x] 新功能

## 测试
- [x] 单元测试已添加
- [x] 所有测试通过
- [x] 验收标准已满足

## 检查清单
- [x] 代码符合 coding 标准
- [x] 测试通过
- [x] 文档已更新
- [x] 关联任务已链接

## 截图
（如果有 UI 变更）
```

### 5. 响应审查

- 收到审查反馈后，认真对待每条意见
- 🔴 阻塞性问题 → 必须修改
- 🟡 建议 → 决定接受或礼貌说明原因
- 修改后 push，PR 会自动更新

### 6. 合并

审查通过后：

1. 确保 CI 通过
2. Squash Merge 到 main
3. 保留有意义的提交信息

---

## 输出

- PR 链接
- 审查报告
- 合并后的提交

---

## 检查清单

```
□ 代码自审完成
□ diff 合理（没有意外改动）
□ PR 描述完整
□ PR 关联了任务
□ CI 流水线通过
□ 审查意见已处理
□ 已合并到 main
```
