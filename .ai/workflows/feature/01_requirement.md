# 步骤 1：需求理解

> **🔍 读取需求规格，确认你对要构建的东西有完整的理解。**

---

## 目标

确保你完全理解功能需求后再进入设计阶段。不清楚的地方现在问，比写了一半发现理解错了要好得多。

---

## 操作步骤

### 1. 读取需求文档

定位并阅读 `specs/<feature-name>/` 下的文件：

```
specs/<feature-name>/
├── prd.md           ← 产品需求（必读）
├── acceptance.md    ← 验收标准（必读，这是"完成"的定义）
└── api.md           ← API 规格（如果有）
```

### 2. 提取关键信息

从 PRD 中提取：

| 维度 | 问题 |
|------|------|
| 用户是谁？ | 谁会使用这个功能？ |
| 解决什么问题？ | 用户现在有什么痛点？ |
| 核心路径是什么？ | 用户最常走的流程？ |
| 边界在哪里？ | 明确不做什么？ |
| 限制是什么？ | 时间、性能、兼容性约束？ |

### 3. 理解验收标准

验收标准是**功能完成的唯一定义**：

- 每一条验收标准都必须被满足
- 如果有标准不清晰或不可测试，现在提出来
- 验收标准就是最终的测试清单

### 4. 确认理解

对自己提问：

```
□ 我能否用一句话解释这个功能？
□ 我能否画出用户的主要操作流程？
□ 我知道哪些部分是重点、哪些是锦上添花吗？
□ 有没有遗漏的依赖或前置条件？
□ 验收标准是否已经可度量？
```

---

## 输出

```markdown
# 需求理解：[功能名称]

## 功能概要
（用一句话描述这个功能）

## 目标用户
（谁会使用？）

## 用户故事
- 作为 <角色>，我想要 <功能>，以便 <价值>
- ...

## 核心流程
（用户从开始到结束的完整路径）

## 关键验收标准
（最重要的 3-5 条验收标准）

## 模糊点 & 问题
（如果有不清晰的地方，列出问题）
- Q1: ...
- Q2: ...

## 下一步
进入 02_design.md — 架构设计
```

---

## 如果需求文档不存在

如果 `specs/<feature-name>/` 不存在或为空：

1. 提醒用户：**"功能开发需要 PRD 和验收标准。是否要我先帮你创建需求文档？"**
2. 如果用户同意，使用 `.ai/templates/spec-template.md` 创建需求文档
3. 需求文档确认后再回到本步骤

```
□ 模糊点已提出
```
