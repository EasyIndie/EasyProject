# 文档标准

> **📏 什么样的代码算"有文档"。**

---

## 核心原则

```
如果代码没有文档，代码就是不完整的。
If it's not documented, it's not done.
```

---

## 文档层次

| 层次 | 位置 | 受众 | 内容 |
|------|------|------|------|
| 项目级 | `README.md` + `docs/` | 所有人 | 项目是什么、怎么开始 |
| 架构级 | `architecture/` | 开发者 | 系统设计、数据流 |
| 功能级 | `specs/<feature>/` | 开发者 + PM | 需求、验收标准 |
| 接口级 | 代码注释 | 调用者 | API 怎么用 |
| 实现级 | 行内注释 | 维护者 | 为什么这样做 |

---

## 必须文档化

### 新功能

```
specs/<feature>/
├── prd.md           # 产品需求（做什么、为谁做）
├── acceptance.md    # 验收标准（怎样算完成）
└── api.md           # API 规格（如果涉及 API 变更）
```

### 公共 API

每个公开的函数、方法、类、接口、端点必须用文档注释说明：

- 做什么（一句话概述）
- 参数（类型、约束、默认值）
- 返回值（类型、含义）
- 抛出的异常（什么时候抛、为什么）
- 使用示例（如果用法不显而易见）

### 架构决策

满足以下任一条件的决策必须创建 ADR：
- 影响系统架构的重大选择
- 有多种替代方案
- 未来可能被质疑"为什么这样做"

### 每个目录

每个目录必须有 `README.md`：
- 目录用途
- 放什么/不放什么
- 命名规范
- AI Agent 交互指南

---

## 文档位置决策树

```
这个信息应该放在哪里？

是需求/用户故事？           → specs/<feature>/prd.md
是验收标准？               → specs/<feature>/acceptance.md
是架构设计？               → architecture/
是重要技术决策？            → architecture/adr/
是编码/API/测试规范？       → docs/standards/
是如何部署？               → docs/deployment.md
是常见问题？               → docs/faq.md
是公共 API 怎么调用？      → 代码中的文档注释
是为什么代码要这样写？      → 行内注释
是目录说明？               → 该目录的 README.md
```

---

## 文档更新时机

| 事件 | 更新内容 |
|------|----------|
| 新功能开发 | 创建 `specs/<feature>/` |
| API 变更 | 更新 `docs/api.md` + 代码注释 |
| 架构调整 | 更新 `architecture/system.md` + 创建 ADR |
| 新工具/库引入 | 更新 `.ai/context/tech-stack.md` |
| 重大代码重构 | 更新相关目录的 README |
| 部署方式变更 | 更新 `docs/deployment.md` |
